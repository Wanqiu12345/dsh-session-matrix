# 32 · 压缩预警指标设计调研

> 调研日期：2026-11-19。目的：为「上下文压缩预警 / 交接建议」功能做多指标设计。
> 结论先行：**压缩次数可以拿到了**（此前 docs/18 的「拿不到」结论在日志层面不成立），
> 多指标判定矩阵可行，业界共识与用户直觉一致——**占用率只是入场券，压缩次数才是降级的主指标**。

---

## 1. DSH 底层事实（从 app.asar 源码确认）

### 1.1 压缩检查点（checkpoint）机制——本次核心发现

`@deepseek-ai/dsh-compaction/src/checkpoint.ts`：

- **每一次压缩完成后，宿主会在会话里写入一个检查点 user message**，
  其 `MessageSource` 携带 `{ kind: 'compact-checkpoint', compactionId }`；
- 该消息**持久化在会话日志**（session.v4.jsonl.zstd）里，压缩只 shadow 旧事件，不删除；
- 手动 `/compact` 的检查点额外带 `sourceCommandId`（自动与手动可区分）。

**真实日志验证**（本机 5 个会话）：

```
session-e2675a3e…  9 个检查点（时间戳链完整可数）
session-9f88038f…  6 个
session-9778930b…  3 个
session-4b675ec9…  1 个
session-593265dd…  1 个
```

检查点事件形态：`type: "user/message"`，`data.source.kind = "compact-checkpoint"`，
`data.source.compactionId` 为 UUID，`time` 为压缩发生时刻（可算频率）。

**这推翻了 docs/18 §7 的「压缩次数拿不到」结论**——那个结论在宿主投影层面成立
（确实没有 compaction 投影，`contextTimeline.requests` 环形缓冲只留 2 条），
但在**持久化日志层面不成立**：日志里有完整的检查点链。

### 1.2 压缩器家族与 meter

- `dsh-compaction`（契约层）：CompactionId / checkpoint / tool-pairing / types；
- `dsh-compaction-basic`（默认策略）：region 压缩，`shadowedSeqs` 保留原事件不删除；
- `dsh-compaction-image-offload` / `dsh-compaction-tool-result-pruner`：辅助压缩器；
- `dsh-token-meter`：统一 pressure/surface 测量（`meter.measure(session)`）。
- 压缩点公式（README 与我们一致）：`messageBudget = window − reservedCompletionTokens`，
  预警阈值 = 压缩点 × 0.8 / × 0.92。

### 1.3 数据获取路径（设计依据）

| 信号 | 来源 | 状态 |
|:--|:--|:--|
| 占用率 ratio | `contextPressure` 投影 + 增量 | 已接入 |
| 压缩点 | `compactPointOf(window, output)` | 已接入 |
| **压缩次数** | 日志扫描 `compact-checkpoint` 标记 | **新发现，可实现** |
| 压缩时间戳链 | 检查点事件 `time` | 新发现，可实现 |
| 刚压缩瞬时信号 | surface ≪ sampled | 已有机制 |
| 轮次 / 步 | `tokenUsage` / `sessionStats` | 已接入 |
| 活跃天数 | `activityDays` | 已接入 |

日志解析本来就走我们的 `decompressFrames` 管线（按预算分摊），加一个
「统计 `compact-checkpoint` 标记」是每帧一次 `includes` 的成本，几乎免费。

## 2. 业界通用设计（Claude Code 生态为主）

- **三级阈值**是通行做法：~70% 主动压缩 / ~90% 用户警告 / ~98% 阻断（Claude Code 的
  `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` 可调）；社区建议在 60–75% 主动手动压缩，
  因为此时摘要质量最高。
- **压缩次数被明确当作降级主指标**（Trail of Bits 指南）：*"Two compactions in a single
  session indicates the task was scoped too large. At this point, /clear and restart
  with better scoping."* —— 两次压缩 = 任务切分失败的信号，应重启而不是硬撑。
- 实践者的分级行动表：85% 建议**手动交接**、95% **强制交接**——即占用率决定「何时」，
  压缩历史决定「要不要」。
- **Context rot 研究**（NoLiMa / Chroma 2025）：1K→32K 时 11/12 模型跌破短上下文性能的
  50%；每多一次压缩，细微决策与引用关系再丢一层。压缩是**有损的且损失可叠加**。
- 轮次退化阈值：15–25 轮后开始遗忘早期约束；连续失败注入的错误噪声是另一种与压缩无关
  的上下文退化（failure-triggered drift）。

**共识归纳**：占用率回答「什么时候会压缩」；**压缩次数回答「这个会话还能不能干好活」**。
两者必须分开判定，且次数的权重更高。

## 3. 设计方案（建议）

### 3.1 判定矩阵（交接建议 = f(占用率, 压缩次数, 压缩新鲜度, 轮次)）

| 压缩次数 | 占用 < 注意线 | 注意~临界 | ≥ 临界线 |
|:--|:--|:--|:--|
| **0 次**（含新会话） | 正常 | 注意：接近压缩点，仍完全可用 | **注意⁺：首次接近**——提示语强调「还没压缩过，历史完整」，不推交接 |
| **1–2 次** | 正常 | 注意：已压缩 N 次 | **临界：建议交接**——「已压缩 N 次，细节正在流失」 |
| **≥3 次** | 注意：历史已多次重建 | 临界：建议交接 | **强烈建议立即交接**——社区共识「≥2 次 = 范围失控」 |

- 「首次接近」正是用户强调的语义：新会话第一次到达临界，历史一次都没压过，
  上下文**完全可用**，此时推交接是误报。
- 压缩时间戳新鲜度：最后一次压缩发生在最近 ~10 分钟内时，摘要最新鲜，
  临界提示可降半级（「刚完成第 N 次压缩，暂无需交接」）。
- 轮次（15–25 轮退化阈值）作为加乘项：高轮次 + 高占用可以在未达临界时提前提示。

### 3.2 数据实现

1. 日志管线（`index.js` 的 split 读取处）每帧统计 `compact-checkpoint` 出现次数与最后时间 →
   `row.compactions`、`row.lastCompactionAt`。零额外 IO，复用现有预算分摊。
2. `riskLevel` 扩展为 `handoffAdvice(ratio, point, cfg, { compactions, lastCompactionAt, turns })`，
   返回 `{ level, reason }`——reason 进交接弹窗「为什么」，按会话个性化。
3. 未解析到日志的会话（预算未覆盖 / 无日志）：压缩次数未知 → 维持现有单指标行为，
   并在弹窗注明「压缩次数未知」。诚实降级，不猜。

### 3.3 UI 文案方向

- 徽标：正常 / 注意·首次接近 / 注意·已压缩 N 次 / 临界·建议交接 / 临界·强烈建议。
- 交接弹窗「为什么」按会话生成，例：*「这个会话已压缩 3 次（最近一次 2 小时前），
  早期细节只剩摘要；占用又回到临界线。历史重建的边际损失已经叠加，建议现在交接。」*
- 顶栏圆点沿用，但只对「建议交接」及以上点亮。

### 3.4 边界情况

- 手动 `/compact` 也产生检查点——计入次数（用户主动压缩同样是历史重建）。
- 会话从别的窗口/机器压缩：日志是同一份，计数不受影响（日志在本机会话目录内）。
- 日志被预算延迟解析期间计数可能滞后 → 弹窗显示「压缩次数未知」而非 0。
- 未来宿主若提供 compaction 投影，`compactions` 数据源可无缝替换（接口已抽象在 row 上）。
