## P0-1 · 原生 Conversation 的 phase

**结论：不是 bug，是 API 边界。**

原生 `ConversationMainPanel` 的算法（asar 原文）：

```js
const shellPhase = session===undefined || conversation===undefined ? 'blank' : conversationPhase(session, conversation)
const settling = sessionId!==undefined && shellPhase==='blank' && openState==='loading' && summaryBlank!==true
const hero     = sessionId===undefined || (shellPhase==='blank' && (openState==='open' || summaryBlank===true))
renderFactorySlot('conversation.content', { variant:'embedded', phase: settling?'settling':hero?'hero':'active', hero })
```

说明三个相位确实存在，且由 `shellPhase` + `openState` + 列表的 blank 标记共同决定。

我们这边实测了 pane 插槽实际注入的 props：

```
useContextMenu | usePanelInfo | useSessions | useSessionStatus | useWorkspaces
useResource | useRemoteAccess | useSessionRetainInfo | useSessionAccess
useWorkspaceAccess | renderFactorySlot | t | renderSlot | SessionProvider | children
```

- **没有 `sessionId`**，所以拿不到 `useSessions(s => s.byId[id])` 里的 blank。
- `useSessionStatus` 是真 hook，签名是 `useSessionStatus(snapshot => snapshot.get(sessionId))`，
  但它返回的是**运行态**：`{ running, pendingInteraction, completionUnread }`，不含 `openState` / `blank`。
- 试过在属性里内联调用，React 抛 #310（hook 数量前后不一致）——说明它必须在顶层无条件调用，
  不能挂在 `ready` 之后。

**结论**：`phase` 保持常量 `'active'`。理由写进了代码注释：面板只列非空白、已打开的会话，
正是 `active` 的适用面。若将来 DSH 在 pane props 里给出 `sessionId`，可以按原生三行公式还原。

**未改行为**，只加了注释与 `data-phase` 属性（便于以后排查）。

## P0-2 · 多 Pane 的 retain 生命周期

**结论：代码层面通过审查；StrictMode 与并发场景待实测。**

现有实现（`lib/client.js`，`NativePane` 的 effect）：

- `retain(id, { source, signal })` 拿句柄，`ref.ready` resolve 后才 `setReference`。
- 清理函数：`controller.abort()` → `ref.release()`（`try/catch`）。
- `ready` 的 then 里检查 `controller.signal.aborted`，避免卸载后 setState。

以下几点是机制上成立的：

| 场景 | 机制 | 判断 |
|:--|:--|:--|
| StrictMode 双挂载 | 第一次挂载 retain A，卸载 abort+release A；第二次 retain B | 通过（依赖 release 幂等，已 `try/catch`） |
| 快速切会话 | effect deps `[id]`，切换即清理旧的 | 通过 |
| 关一个 Pane | 每个 Pane 各自持有句柄，只释放自己那份 | 通过（依赖 DSH 引用计数，未在 UI 实测） |
| 卸载漏清理 | signal 是兜底 | 通过 |

**待实测**：两个 Pane 同跑、关一个看另一个是否继续——需要真实驱动 UI 发消息，当前环境只能做人工验证。

**潜在风险**：`abort()` 与 `release()` 双路径，若 DSH 在 abort 时已释放且 release 不幂等，会二次释放。
代码已 `try/catch`，但语义上仍依赖宿主的幂等性。

## P1-3 · 压缩点公式（已确认问题，已修）

原实现：`min(window × 80%, window − maxOutput − 64K)`。
DSH 真实策略（asar 中 `dsh-compaction-basic`）：

```
messageBudget  = contextWindow − reservedCompletionTokens
pressureBudget = messageBudget − policy.headroomTokens     // headroomTokens = 4096
```

- `retainRatio: 0.16` 是**压缩后保留多少**，不是触发阈值——这是原来 0.8 那个系数的误读。
- 64K headroom 是我们的猜测，真实值是 4,096。

影响：1M 窗口 / 256K 输出，旧值 **69.3%**，实际 **75.2%**（788,480 tokens）。旧版本会提前约 6 个百分点报警。

改动：`lib/index.js` 去掉 `COMPACT_RATIO`，`COMPACT_HEADROOM = 4096`；`compactPointOf` 改为
`window − output − 4096`，窗口小于预留时返回 `null` 而不是负数。
新增用例：`compaction point mirrors dsh-compaction-basic`（断言 1M − 256K − 4K）。

**剩余风险**：`reservedCompletionTokens` 我们取 `maxOutputTokens`。若某模型路由层面的预留值与最大输出不同，
压缩点会有偏差；这一点宿主没有暴露，无法验证。

## P1-4 · Host API 的鉴权（已确认高危，未修复）

实测（同一实例，同一端口）：

| 请求 | 结果 |
|:--|:--|
| `GET /api/session-matrix/overview`（无 token） | **200** |
| `GET /api/session-matrix/capabilities`（无 token） | **200** |
| `GET /api/session-matrix/overview?token=wrong` | **200** |
| `GET /api/sessions`（原生，无 token） | 401 |
| `GET /api/health`（原生，无 token） | 401 |
| `GET /`（页面，无 token） | 401 |

也就是说：**原生 API 全部要求 token，我们注册的三个 `resource` 路由完全不校验**。
能访问端口的人可以读到会话标题、项目名、上下文用量、费用。

`ctx.webServer` 的公开面是 `register / registerUpgrade / registerFallback / readResource / tapIndex /
responderFor / match / serveResource`，没有显式的 auth 帮助方法；`register({kind:'exact', path, resource})`
是"静态资源"语义，可能因此绕过了鉴权中间件。

**未修原因**：改注册方式需要 DSH 未公开的选项（`kind` 的枚举、或 `auth` 标志），猜错会让路由 404，
比现状更糟。**缓解现状**：宿主默认只监听 `127.0.0.1`，非隧道/反代场景外部不可达。

**建议修法**（需 DSH 文档或源码确认其一）：
1. 用带鉴权的注册方式（若存在 `handler` / `auth: true`）；
2. 在 `resource` 内自行校验 `request` 上的 token（需先确认 token 从哪个服务可取）；
3. 至少把响应裁剪为不含项目名与路径的字段。

**验证方法**：改完后重复上表四条 curl，未带 token 必须 401。

## P1-5 · 多会话真实运行测试

**结论：未自动化，给人工清单。** 现有 30 条契约测试只覆盖宿主侧 DTO，不覆盖原生 UI。

人工验证清单（每次发版前跑一遍，20 分钟）：

1. 拖两个会话进窗格，同时各发一条消息，两边都在流式输出。
2. 只让左边跑，右边空闲，确认右边的输入框仍可用、无额外占用。
3. 关掉左边窗格，确认右边继续输出到结束；再打开三条，重复。
4. 选中一个子代理节点，核对「会话概览」里的用量 ≈ 父会话 + 子代理之和。
5. 在窗格里触发一次工具审批，确认弹窗出现在**那个窗格**而不是别的窗格。
6. 窗口拖到 900px 以下，确认窗格折叠、无横向滚动条。
7. 四格全跑时看任务管理器：内存增长应收敛，DPR 2 下滚动不卡。
