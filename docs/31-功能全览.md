# 31 · 功能全览 —— 给宣传视频 Agent 的完整素材

> 这份文档是给「负责制作宣传视频的 Agent」看的。目标：不看代码也能准确说出这个插件的
> 每一个功能、每一个按钮、每一处数据的来源，以及宣传时**能说什么、不能说什么**。
> 所有按钮名、提示语均为 UI 中的**逐字文案**（简体中文界面）。

---

## 0. 一句话定位

**会话矩阵工作台（DSH Session Matrix）** 是 DeepSeek Harness（DSH）的一个插件：
让用户**同时运行多个 AI Agent 会话**，用四格原生对话并排处理并行任务，用一张图看清所有会话
的上下文风险，并在上下文被自动压缩**之前**把工作交接出去。

### 它解决的六个真实痛点

| 痛点（原生 DSH 的状态） | 插件给出的答案 |
|:--|:--|
| 多任务时只能盯着一个会话，来回切换 | 1–4 格**原生**对话窗格并排，四格之间零切换成本 |
| 子代理像黑盒：跑在哪个主会话下、干了多少活看不见 | Agent Graph 把「主会话 → 子代理」的父子链画出来，节点大小 = 用量 |
| 上下文压缩无声发生，改到一半的历史突然被摘要替换 | 三级风险色（正常/注意/临界）+ 精确压缩点算法，提前预警 |
| 交接全靠口述：「你把刚才的思路发给新会话吧」 | 交接协议 v1：一键生成提示词 → Agent 自己写出七节结构化交接文档 |
| 花了多少钱是黑盒 | 人民币计价的预估费用，峰时 ×2 规则明确，缓存命中单独算 |
| 费用类插件强依赖另一个插件 | 对 `dsh-context` **零依赖**：没有它，费用从会话日志重建，口径一致 |

### 视频里可以用的硬数字（全部可验证）

- 最多 **4 栏**原生会话（`MAX_PANES = 4`）
- 窗格缩放四档：**55% / 70% / 85% / 100%**，按会话记忆
- 1,048,576 窗口 + 256,000 输出预留的模型，压缩点 = **788,480 tokens（75.2%）**
- 注意线 = 压缩点 × **80%**，临界线 = × **92%**
- 面板数据 **45 秒**缓存，打开面板期间每 **15 秒**自动刷新
- 日志解析预算：每轮 **6 个文件 / 8 MB**，单文件上限 **32 MB**（超出会明确报告）
- **0 个**运行时依赖，整个插件就是两个 JS 文件 + 一个 SVG 图标，无构建步骤
- 3 个 API 接口，全部走宿主认证通道

| 位置 | 出现什么 | 视频镜头建议 |
|:--|:--|:--|

## 2. 视图一：工作区（`viewWorkspace`）

这是主战场。左窄右宽两栏，中间分隔条可拖（宽度写进 `localStorage`）。

### 2.1 左栏：会话列表

- 顶部搜索框，占位文案逐字：**「搜索会话、模型…」**
- 筛选：**「全部」** / 按项目名（多项目时逐个列出）
- 会话按**项目分组**；子代理折叠在所属主会话之下
- 每行显示：标题（无标题则显示「未命名会话」）、模型名、风险色点、占用率
- **归档会话不显示**——与原生侧栏行为一致；在原生侧取消归档，这里下次刷新就回来
- 列表底部统计条：`N 个项目 · N 个会话 · N 条父子链路`
- 列表右缘有一条拖动条，提示逐字：**「拖动调整列表宽度」**

### 2.2 右栏：1–4 格原生窗格

| 格数 | 布局 | 适合场景（宣传口播可用） |
|:--:|:--|:--|
| 1 | 单格铺满 | 专心做一件事 |
| 2 | 左右两列 | 对照两份输出，或主会话 + 子代理 |
| 3 | 上二下一 | 三个并行任务，底格看汇总 |
| 4 | **2×2** | 四个项目同时推进 |

**首次进入就是 2×2 四格全空**——这是刻意设计：插件不猜用户想看哪个会话，
每格显示逐字提示：**「从左侧选择一个会话」**，副文案：
**「点左侧任一会话，这里直接嵌入它的原生对话；同一个会话只占一个窗格，最多 4 栏」**。

**关键卖点：窗格里是 DSH 原生 `conversation.content` 工厂实例。**
消息流、工具调用行、审批按钮、Chat/Trajectory 切换、底部 composer 全是原生的，
**可以直接打字发消息**——不是一个只能看的截图墙。

**唯一的例外**：子代理会话的窗格是**只读**的，右上角有逐字徽标 **「只读 · 子代理」**，
悬停说明：**「子代理会话：可以查看，但不能在这里直接发消息」**。视频里如果演示向子代理发消息就是错的。

### 2.3 每格的操作（按钮逐字）

| 按钮/元素 | 行为 |
|:--|:--|
| 标题栏居中的**缩放滑块** | 四档：55% / 70% / 85% / 100%，按会话记忆；悬停说明逐字「内容缩放 N%（只改变显示大小，不影响会话）」 |
| **「关闭」**（每格右上角 ×） | 关掉这一格，其余格子重排 |
| **「在原生界面打开」** | 跳回 DSH 原生单会话界面 |
| 顶部 **「分栏」**（＋） | 加一栏，最多 4 |
| 顶部 **「减少一栏」**（−） | 减一栏，最少 1 |
| 左右分隔条 | 提示逐字「拖动调整左右宽度」；上下分隔条「拖动调整上下高度」，比例持久化 |

同一会话不会被重复打开（一个会话只占一个窗格，防呆写在代码里）。

### 2.4 一个隐藏的演示亮点：**「模拟预警」/「恢复真实值」**

列表顶部有个按钮，逐字 **「模拟预警」**，点一下整张图/列表会**临时把所有会话渲染成预警状态**，
按钮变成 **「恢复真实值」**。
这是给新用户**一眼看清预警长什么样**的演示模式——视频里强烈建议用：正常状态灰蒙蒙看不出对比，
模拟一下，红黄立刻铺满，视觉冲击最强。

## 3. 视图二：智能体脉络（Agent Graph，`viewCockpit`）

一张**四列有向拓扑**，从左到右：

```
工作台 → 项目 → 主会话 → 子代理
```

列标题逐字：**「工作台」「项目」「会话」「子代理」**；列之间画连线。
画布空白处提示：**「点击网络中的任一节点查看详情」**。

### 3.1 数据口径（宣传时要说准）

- **连线只来自会话头的 `parentSession` 字段**——真实的父子关系，不是「同项目」这类猜测。
  底部图注逐字：`N 个项目 · N 个会话 · N 条父子链路 · 0 条跨分支关联（数据源无此关系，不绘制）`
  ——这句「0 条」是诚实声明：插件不编造它没有的数据。
- **节点颜色 = 距压缩点远近**：正常（灰）/ 注意（黄）/ 临界（红）/ 无数据。
- **节点尺寸 = 累计用量**：谁最重一眼可见。
- 跨项目、未归类会话归入 **「未归类」** 节点；归档会话不画。

### 3.2 选中节点的联动（宣传核心镜头）

点任一节点，下方**三个模块**按该节点的**子树**重新汇总（选主会话 = 它 + 它的子代理们）：

#### 模块一：上下文构成（`composition`）

回答「**此刻模型看到了什么**」。当前 prompt 按 **7 类**拆分，横向堆叠条 + 图例，逐字名称：

```
系统提示 · 工具定义 · 用户输入 · 注入内容 · 技能目录 · 助手回复 · 工具返回
```

底部注释逐字：**「构成比例由事件逐条估算；总量按服务端返回的 prompt 校准，所以各项之和等于顶部那个数」**。

#### 模块二：累计用量与费用（`usageTitle` 逐字：**「累计用量与费用」**）

回答「**这个会话一共烧了多少**」。四个 token 桶 + 请求数，逐字标签：

```
输入 · 输出 · 缓存读 · 缓存写 · 请求
```

外加 **「预估费用」**（人民币）和 **「缓存命中」** 百分比。
底部注释逐字：**「费用按人民币 · 峰时 2 倍 · 官方价目表」**。

#### 模块三：会话概览（`matrix`）

回答「**每个会话现在什么状态**」。表格三列：**「项目」「会话」「子代理」**，
每行：标题 / 模型 / **「上下文占用」**（已用/容量）/ 风险 / **「轮次 / 步」**。
行可点击 —— 直接把会话载入一个窗格。

### 3.3 一个必须讲清的口径区别（视频脚本别写错）

**「上下文占用」≠「累计用量」。**

- 上下文占用 = **此刻**模型视野里占着多少 token（快照，会话进行中会滚动）
- 累计用量 = **历史上一共**读写了多少 token（只增不减，包含缓存读写）

UI 里两处都叫「上下文占用」时带了不同的解释气泡：
占用处逐字 **「上下文占用 = 已用 / 容量（与服务端状态栏同口径）」**；
累计处逐字 **「会话开始至今的累计计费 token，与上面『当前上下文』不是同一口径」**。
宣传脚本若混用这两个词，懂行的观众一眼看出不对。

## 4. 上下文监控：压缩点是怎么算的

这是插件技术上最硬的部分，视频可以用一段动画讲：

```
messageBudget  = contextWindow − reservedCompletionTokens   # 给模型回复留的输出空间
pressureBudget = messageBudget − policy.headroomTokens      # headroom 默认 4096
```

- 公式**照搬 DSH 官方 `dsh-compaction-basic` 插件**，不是自己拍的百分比
- 1,048,576 窗口、256,000 输出预留 → 压缩点 **788,480 tokens = 75.2%**
- 早期版本用过 `min(window×80%, window−output−64K)` 的估算式，会**提前**于 DSH 真实触发点
  预警——已改成与官方一致

| 阈值 | 计算 | 含义 |
|:--|:--|:--|
| 🟡 注意 | 压缩点 × 80% | 还装得下一次较长回复 |
| 🔴 临界 | 压缩点 × 92% | 下一次大请求很可能触发压缩 |

**0.17.0 起：压缩次数是第二指标**（措辞必须按此更新）——占用率只回答「何时压缩」，是否值得交接看压缩次数：

- 从未压缩过的新会话首次到达临界 → 标「**首次接近**」，历史完整可用，**不推交接**；
- 已压缩 2 次再达临界 → 「临界，建议交接」；≥3 次一过注意线就升级；
- 刚压缩完 10 分钟内提示自动降半级；未解析到日志的会话如实显示「压缩次数未知」。
占用率的分子取**服务端返回的 prompt 实际大小**（未命中 + 缓存读 + 缓存写），
再叠加最后一次采样后的增量——**不用字符数估算**。

风险四级逐字：**「正常」「注意」「临界」「无数据」**（无数据 ≠ 正常，是诚实标注）。

## 5. 通用交接提示词（Handoff Protocol v1）

**按钮位置**：面板右上角。**逐字名称：「通用交接提示词」**。
悬停说明逐字：**「换模型、换 Agent、今天先收工，用得上就来复制。」**
旁边的**小圆点**显示有几个会话进入注意/临界区。

### 5.1 解决什么

上下文压缩会把早期对话换成摘要，而最先丢的恰恰是接手者最需要的：
**路径、命令、报错**。交接协议让 Agent 在压缩**之前**自己写交接文档。

### 5.2 使用流程（视频按这四步拍）

```
① 点「通用交接提示词」→ 弹窗里点「复制」
② 把提示词发进目标会话
③ Agent 自检 → 提取状态 → 盘点落盘 → 写出 HANDOFF-<时间戳>.md
   （目标 / 进度 / 关键文件 / 已否决方案 / 未决问题，七节结构）
④ 新会话粘贴接管消息，无缝续做
```

弹窗文案逐字（都是「只读、不动你数据」的声明，适合口播强调）：

- **「只复制，不发送、不改动任何会话」**
- **「点开看看、改改、复制走。不会替你发送，也不会动任何会话。」**
- 用法行：**「复制 → 回本会话发送 → 它给出接管消息 → 新会话粘贴」**

### 5.3 协议里的两个安全设计（值得单独一镜）

1. **会话自检**：协议第一步要求 Agent 核对当前会话标题是否就是用户要交接的那个，
   不对就停下来问——防止提示词贴错会话。
2. **落盘纪律**：重要成果必须已保存在磁盘；**不写 API Key、密码、Cookie**，
   工作区有 `.env` 只记文件名不读内容。

### 5.4 「载入窗格」闪烁

复制提示词时如果目标会话还没开在窗格里，会弹一条通知：
**「交接提示词已复制 · 《标题》没有在窗格打开」**，带按钮 **「载入窗格」**。
点它，目标窗格自动载入该会话并**闪烁三次**（0.78s × 3，尊重系统减动效设置），
防止用户粘错会话。

## 6. 费用口径（人民币）

| 模型 | 缓存命中 | 缓存未命中 | 输出（元/百万 token，谷时） |
|:--|--:|--:|--:|
| DeepSeek V4.1 Flash（`deepseek-flash`，旧名 `deepseek-v4-flash`） | 0.02 | 1 | 4 |
| DeepSeek V4 Pro（`deepseek-v4-pro`） | 0.15 | 4.5 | 13.5 |

- **峰时 ×2**：北京时间工作日 09:00–12:00、14:00–18:00，节假日除外
- 非 DeepSeek 模型回退 models.dev 的美元价，按 **1 CNY = 0.15 USD** 折算
- 数据来源三级降级：① 若安装了 `dsh-context`，直接用它的峰谷分桶投影；
  ② 没有则**从会话日志逐帧重建**（每条请求带时间戳和用量）；
  ③ 都不行才用 `peakFactor` 兜底（默认 1）
- 口径声明：这是**预估费用**，不是账单

### 与 dsh-context 的关系（视频容易踩的坑）

`dsh-context` 是另一个社区插件（上下文分析）。本插件**参考过它的口径设计并公开致谢**，
但**不是依赖**：不装它，本插件全部功能照常工作。两者可同时装、数字可对账。
宣传时**不要说**「基于 dsh-context」或「需要 dsh-context」。

## 7. 底层逻辑（给视频的"技术背书"镜头或旁白）

### 7.1 架构

- **两个 JS 文件**：`lib/index.js`（Host 半边，注册服务与接口）+
  `lib/client.js`（Client 半边，UI），**零运行时依赖、零构建步骤**
- 通过 DSH 公开的 Cordis 服务与 slot 扩展点接入，**不改宿主任何代码**
- 兼容 DSH `>= 0.2.2-rc.1`，Node `^22.19.0 || >=24`（依赖 zstd API）

### 7.2 数据接口与安全

- 三个接口：`overview`（全量数据）、`capabilities`（能力/版本）、`handoff`（交接提示词）
- 全部注册在 `connection.fetch` 上 → 走宿主统一认证：**无凭证 401，非 owner 403**
- **宿主缺 `connection` 时一个路由都不注册**——绝不静默降级成无鉴权接口（有专门测试锁死）

### 7.3 性能设计

- 面板数据 45 秒缓存；「刷新」按钮逐字提示：**「立即从宿主重新读取一次（跳过 45 秒缓存）。
  面板开着的这期间每 15 秒自动刷新，…」**
- 日志重建峰谷分桶按预算分摊：每轮 6 文件 / 8MB，几分钟内收敛，之后按文件缓存
- 单文件 32MB 上限；超限会话**明确报告**（接口字段 `oversizeSessions`），不静默漏算

### 7.4 可靠性细节（可作为"我们连这些都想到了"的彩蛋）

- 会话日志是逐次追加的 zstd 帧。解析按 RFC 8878 走**帧结构**而非搜魔数——
  压缩数据里可能出现魔数字节，搜索式解析会把好帧切成两半
- 只解压**结构完整**的帧：正在被写入的尾部帧不完整，直接跳过（宁缺勿错）
- 并发采集合并：同一版本的日志两个请求只读一次
- localStorage 损坏时自动回退默认布局，不会白屏
- React StrictMode 双挂载、快速切换均安全

## 8. 宣传视频 Agent 的工作守则

### 8.1 推荐镜头顺序（30–60 秒宣传片）

1. **痛点**（3–5s）：原生 DSH 单会话界面，任务多了来回点
2. **安装**（3s）：插件管理器搜到 `dsh-session-matrix`，一行安装
3. **进入**（5s）：左侧点「会话矩阵工作台」→ 四格全空的 2×2 → 从左侧点四个会话依次点亮
4. **并行干活**（8s）：四格同时滚动输出，其中一格是子代理
5. **切到「智能体脉络」**（8s）：全图 → 点一个主会话 → 三模块联动 → 红色临界节点特写
6. **模拟预警**（4s）：点「模拟预警」→ 全图变红黄 → 「恢复真实值」
7. **交接**（10s）：右上角按钮 → 复制 → 窗格闪烁 → Agent 写出 HANDOFF 文件
8. **费用**（5s）：「累计用量与费用」模块特写（¥ 金额 + 缓存命中）
9. **收尾**（5s）：npm 包名 `dsh-session-matrix`、零依赖徽标、开源 MIT

### 8.2 措辞红线（说错会被社区指出来）

| 能说 | 不能说 |
|:--|:--|
